# 摘要

本项目是一个面向编程初学者的代码学习助手，帮助学习者在「看不懂、找不到错、不知道练什么」三个环节获得即时帮助。

与直接向通用大模型提问不同，本项目把工作拆成两部分：**确定性的结构化工作在程序里完成**（语法识别、报错堆栈解析、错误类型匹配、语言检测），**自然语言生成交给大模型**（讲解、改法、练习）。模型的输出必须落在程序给定的结构里，不许自由发挥。

技术栈为 Next.js 16 + React 19 + TypeScript（共 3204 行），通过服务端 Route Handler 调用智谱 GLM 模型并重新封装为 SSE 流式响应；服务端密钥不下发浏览器，按访问 IP 做尽力而为的额度限流，所有错误信息统一脱敏。

开发过程全程与 AI 协作完成，保留了 3 条完整的 Prompt 迭代记录与约 110 KB 的完整对话导出（见 `docs/ai-log/`），其中 3 条链是安全缺陷的发现与加固过程。

我做这个项目的起因很具体。有一次上 Java 课，有几段代码我没看懂——课上还能问老师，下课自学时就麻烦了。而普通的 AI 工具只能一问一答，问完这一次，它并不知道我在学哪一章、卡在哪一类问题上，下次还得从头解释一遍。**我缺的不是一个能回答问题的工具，而是一个能跟着我学的。**

# 2. 问题与场景

## 2.1 目标用户与真实困难

目标用户：**刚开始学编程的学习者**（本项目作者本人即是其中之一）。

| 卡点 | 具体表现 | 现有做法的不足 |
|---|---|---|
| **看不懂** | 代码能跑，但不知道每一行在干什么 | 教材按知识点组织，不按你手上这段代码组织 |
| **找不到错** | 报错信息是英文堆栈，看不懂术语 | 搜索引擎给出的是别人的问题，未必是你的 |
| **不知道练什么** | 看完了，但没有对应练习 | 需要有人按当前知识点出题 |

学数组那一章的时候，我写了一个 `switch`，运行起来就报错了。控制台给我的是一段英文，我看不懂；问同学，同学也说不太清。最后自己在网上搜了半天才弄明白，**是 `case` 后面的类型不匹配** —— 编译器其实一直在提示那里有问题，但我读不懂它在说什么。前后花了一个多小时。

回过头看，我卡住的地方主要不是「不会写」，而是「看不懂」—— 看不懂别人的代码，也看不懂自己代码的报错。而当时能用的工具帮不上这个忙：教材是按知识点组织的，不是按我手上这一段代码组织的；网上的答案是写给会看堆栈的人看的。

> 写作提示：这是全文最能让评委共情的部分。不要写「编程初学者面临诸多困难」这种话。

## 2.2 为什么不用「直接把代码贴给 AI 问」

**差异不在「能不能回答」，在「回答的形状」。**

| | 直接问通用大模型 | 本项目 |
|---|---|---|
| 输出形态 | 一段自由文本，每次结构不同 | 落在程序定义的**区块结构**里（讲解/根因/改法/练习） |
| 报错定位 | 模型自行判断行号 | **程序用正则解析堆栈，行号由代码算出** |
| 语言识别 | 模型自行判断 | **程序按扩展名与关键字判定**（`languageDetect.ts`） |
| 常见错误类型 | 每次现想 | **本地错误知识库匹配**（`errorKnowledge.ts`，309 行） |
| 是否可以逐段渲染 | 否 | 是（按区块渲染，可折叠、可复制） |
| 出错后是否可追溯 | 否 | 是（5 条 Prompt 记录 + 32 条提交） |

**核心差异一句话：确定性的部分交给程序，生成性的部分交给模型。**

# 3. 产品设计与功能

## 3.1 四种辅导模式

| 模式 | 输入 | 输出要求 |
|---|---|---|
| 逐行讲解 | 一段代码 | 按行解释，不许跳行、不许省略 |
| 找 Bug | 一段代码 + 可选报错 | 指出问题所在行 + 原因 + 修改建议 |
| 优化重构 | 一段代码 | 给优化后代码 + 说明改动理由 |
| 出练习题 | 知识点或代码 | 给题目 + 参考答案 + 考察点 |

四种模式的系统提示词定义在 `src/lib/modes.ts`（66 行），**每种模式是一段独立的约束文本，而不是一个模式的四句变体**。

## 3.2 主要功能

- **Monaco 代码编辑器**：语法高亮、行号、多语言、`Ctrl+Enter` 发送
- **流式回答**：逐字输出，可中途停止（停止后保留已生成内容）
- **多轮对话**：保留最近 10 条上下文，可追问
- **对话历史**：存于浏览器 `localStorage`，不上传服务器
- **离线错误手册**：内置常见错误类型与处理方案（308 行知识库），**不消耗 API 额度**
- **错误堆栈解析**：识别异常类型、错误消息、出错行号，并附通俗解释
- **模型设置**：可用服务端公共额度，也可填入自己的 Key 与接口地址
- **429 自动重试**：上游模型过载时自动重试一次，避免用户直接看到失败

我最满意的是「逐行讲解」。它会**把每一行代码用通俗的话翻译一遍**，让我真正看懂这段代码在干什么，而不是只给我一个能跑的答案。

「看懂」和「能用」对我来说是两件事：从网上抄一段代码能跑起来，但下次换个场景还是不会写，因为我不知道每一行到底在起什么作用。逐行讲解解决的就是这个。

所以我在提示词里特意写死了两条：**不许跳行、不许省略**。一旦允许它省略，它就会跳过它认为「简单」的行 —— 而那些行往往正是我不敢确定的地方。

## 4.2 前后端职责边界

| 层 | 负责 | 不负责 |
|---|---|---|
| 浏览器 | 交互、状态、历史、渲染、结构化预处理 | **任何密钥** |
| 服务端 | 入参校验、限流、密钥持有、上游调用、流式转写、错误脱敏 | 业务文案、用户数据存储 |

**设计原则：浏览器是「不可信客户端」。** 所有可能被滥用的能力（密钥、外部请求、限流）都必须在服务端边界内。

## 4.3 关键设计一：把结构化工作从模型手里拿走

这是本项目架构上最重要的一条约束。

| 工作 | 交给谁 | 为什么 |
|---|---|---|
| 判断代码是什么语言 | **程序**（按扩展名与关键字） | 确定性工作，模型判断反而会错 |
| 从 Java 堆栈抽出异常类型/消息/行号 | **程序**（正则 + 模式匹配） | 行号必须准确，不能由模型「估」 |
| 匹配常见错误类型与处理方案 | **程序**（本地知识库索引） | 固定知识，不需要每次生成 |
| 解释这个错误是什么意思、怎么改 | **模型** | 需要自然语言与上下文 |

**一句话：能用代码算出来的，不给模型机会。**

**这条设计是实测验证过的，不是设计说明。** 把浏览器开发者工具的网络切到 Offline，再粘贴 Java 异常堆栈：界面正常给出「离线解答 · 未调用 AI」，Network 面板中**没有任何 `/api/chat` 请求**，即整条链路确实没走网络。

同时做了反向验证：粘贴一段不含代码的普通文字描述，确认它**没有**被误判为离线命中，而是照常走 API 流程。这一步比正向验证更重要——不加这一步，就无法排除「离线匹配条件过宽、把正常提问也本地化处理」的风险。

**效果**：模型的输出范围被限制在「解释与建议」，它没有机会把行号算错、把语言认错、把错误类型编错。

**这个分工是从一次具体的不满开始的。**

我在需求里写的是（原文）：

> 当前「找 Bug」模式只能把报错原文直接发给 AI，我想做一个增强：用户粘贴 Java 异常堆栈时，前端自动解析出异常类型、错误消息、出错文件和行号，生成面向零基础学生的通俗摘要，然后把摘要 + 原文一起发给 AI，让回答更精准。

**我的判断是：整段英文堆栈对零基础学生是无效输入。** 学生看不懂
`at java.base/java.lang.Integer.parseInt`，把这坨东西整段丢给模型，模型也只能自己猜哪一行才是真正出错的地方，而且每次猜的还不一样。改成程序解析后，**行号由代码算出来，不是模型估出来的**。

改成程序解析之后，AI 在这一轮里发现了三处我自己没想到的真实缺陷：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | Java 9+ 模块前缀帧（`java.base/java.lang.Integer.parseInt`）被静默跳过 | 若整个堆栈都是这种格式，**出错位置会直接丢失** |
| 2 | 摘要取的是**第一帧** | 若第一帧恰好是 JDK 内部方法（如 `NumberFormatException.forInputString`），**学生会以为错在这一行，被误导** |
| 3 | 中文句子里出现「Exception」字样也会触发解析 | 误报 |

这三条让我把当初的判断坐实了：**解析这种确定性工作必须由代码做，而且必须用真实数据去测。**
如果交给模型，它不会告诉我「这里有三个边界情况」——它只会给我一个看起来能用的结果。

## 4.4 关键设计二：流式响应

实现方式：服务端拿到上游的 `ReadableStream`，逐行解析 `data:` 事件，抽出 `delta.content`，重新封装成自己的 SSE 格式推给前端；遇到 `[DONE]` 关闭连接。

**为什么重新封装而不是直接透传**：透传会把上游的原始结构、模型名、可能的错误细节一起送到浏览器。重新封装后，浏览器只收到 `{"content": "..."}`，**上游信息一律不外泄**。

**前端如何处理流**：用 `\n\n` 分帧、`TextDecoder(stream: true)` 处理跨 chunk 切断的多字节字符、末尾 flush 残留缓冲；任何解析失败的 chunk 静默跳过而不中断整个流。

**中断语义**：用户点「停止生成」时，前端 `abort` 掉请求，但**保留已生成的内容**并追加「（已停止生成）」，而不是清空整条回答。

## 4.5 关键设计三：安全边界

| 安全要求 | 实现 |
|---|---|
| 密钥不下发浏览器 | 只从服务端 `process.env` 读取；前端全程无密钥字段 |
| 错误信息脱敏 | 任何返回给浏览器的错误串中，若含密钥则替换为 `***` |
| 凭据不外泄 | **使用服务端 Key 时，接口地址强制为默认值，客户端传入的 baseUrl 被忽略** |
| 防 SSRF | 自定义地址仅在使用自带密钥时允许；必须 https + 仅 443 + 无账号密码 + **域名白名单** |
| 防重定向绕过 | 上游请求使用 `redirect: "manual"`，3xx 一律不跟随，返回 502 |
| 入参校验 | messages 条数上限 50、单条 20000 字符、role 与 content 类型校验，**校验在限流之前** |
| 滥用防护 | 走服务端额度时按 IP 限流（10 次/分钟、100 次/天） |
| 依赖安全 | `npm audit` 全程保持 **0 vulnerabilities**；Next.js 升级至 16.4.3 修复已知漏洞 |

### 4.5.1 一次真实的安全加固过程

**① 我是怎么发现的**

审查 `/api/chat` 时，注意到三行代码连在一起有问题：

```ts
const baseUrl = (body?.baseUrl ?? "").trim() || API_URL;  // 地址由客户端指定
const apiKey = clientKey || serverKey;                     // 没带 Key 就回落到服务端 Key
upstream = await fetch(baseUrl, { headers: { Authorization: `Bearer ${apiKey}` } });
```

**② 我判断的成因**

两条独立的漏洞，都成立：

- **凭据外泄**：客户端传 `baseUrl` 但不传 `apiKey` 时，服务端会用自己的 `ZHIPU_API_KEY` 去请求客户端指定的地址。攻击者把 `baseUrl` 指向自己的服务器，就能从 `Authorization` 头里读到部署者的 Key。**不需要任何绕过，就是正常的请求组合。**
- **SSRF**：`baseUrl` 完全不受限，可指向内网地址或云元数据接口；而且代码把上游响应体原样流回客户端，攻击者能直接读到内网服务返回的内容。

**③ 我要求 AI 怎么改**

我先要求它**只确认判断、不要改代码**，确认后才给出四条硬约束：服务端 Key 分支强制回退默认地址；自定义地址仅在客户端自带 Key 时可用；白名单 + 仅 https；不得破坏已有的自定义模型功能。

**④ 我怎么验证的**

- **六组攻击载荷**（云元数据 `169.254.169.254`、内网 `192.168.1.1`、`http://`、自定义端口、含账号密码、白名单外域名）全部返回 400
- **服务端 Key 分支**：把 `baseUrl` 指向 `https://127.0.0.1:1/never`（一个必然连不上的地址），若该值被使用则一定失败；实测返回 200 并正常流式输出，**证明 baseUrl 已被忽略**

**⑤ 一个我没有预料到的收获**

复核时我追问「除了这个，你在那次改动里还动过哪些我没明确要求的地方」，AI 承认还修改了前端组件 `ModelSettings.tsx` 的预校验与文案 —— 这属于超范围改动。**这说明「不要破坏现有功能」这种正面约束对模型无效，它会按自己的理解扩大范围；必须写成「除 X、Y 文件外不得修改」。**

（完整对话见 `docs/ai-log/2026-10-23-01-服务端Key外泄与SSRF.md`）

# 5. 意图控制策略　★核心章节

## 5.1 我的提问结构

我固定使用四段式，缺哪段就在哪段出问题：

| 段 | 作用 | 漏了会怎样 |
|---|---|---|
| **目标** | 一句话说清要什么，具体到可验证 | 拿到一个「通用版」，还得自己改 |
| **约束** | 技术栈、路径、**哪些文件不能动** | 模型看不到我的目录，会覆盖或重构 |
| **验收** | 什么算做完 | 自己也没想清楚，交付后无从判断 |
| **禁区** | **不要做什么** | 它会「顺手多做」，我得回滚 |

**为什么「禁区」最有效**：模型天然倾向多给一点。写「只做表格」它会加排序；写「不要做图表、不接入 XX」它就不越界。**负面约束的效果通常强于正面要求。**

此外我逐渐固定了两个习惯：

- **「先确认判断，不要直接改代码」**：逼它先做诊断。否则它会跳过分析直接给一版「看起来能用」的代码。
- **「说明理由，不只是结果」**：例如要求它解释为什么选 `redirect: "manual"` 而不是 `"error"`。给出理由的地方，才是我能审查的地方。

## 5.2 哪些事我不交给 AI

| 不交给 AI | 理由 |
|---|---|
| 脚手架与构建配置 | 版本对齐、目录契约容易配错，且与业务无关，排查成本高 |
| 密钥与环境变量管理 | 一旦让模型「顺手写进去」，就会进代码或进日志 |
| 限流、脱敏、入参校验 | 这些是安全边界，必须由我明确指定规则 |
| 堆栈解析与错误知识库 | 确定性工作，见 4.3 |
| **安全修复的验收用例** | 由我自己构造攻击载荷，不接受「它说修好了」 |

**我实际拦下过的一次「多做」**：要求 AI 修 `baseUrl` 的凭据外泄时，我明确写了四条约束，其中「不得破坏现有的自定义模型功能」。结果它把这个功能的前端预校验和文案也改了 —— 理由是「配套 UX」。虽然动机合理，但**安全修复被扩大到 UI 层，超出了我的授权范围**。我追问后才拿到这份清单，并据此决定保留哪些（见 4.5.1 ⑤）。

## 5.3 三次真实的纠错过程

> 以下三条的完整对话（我的原始提问、AI 回复、我的追问、实测数据）保存在 `docs/ai-log/` 下，此处为摘要。

### 案例一：服务端密钥随自定义接口地址外泄（含 SSRF）

| 段 | 内容 |
|---|---|
| **① 我的提问** | 指出三行代码串联后的凭据外泄与 SSRF，要求先确认判断、再给方案，并给出四条硬约束（服务端 Key 分支强制默认地址 / 自定义仅限自带 Key / 白名单+https / 不破坏已有功能） |
| **② AI 的建议** | 确认两条判断都成立，给出分支强制 + 白名单校验的方案；并主动指出残留风险：`fetch` 默认跟随重定向，若要严谨可加 `redirect: "error"` |
| **③ 我发现的问题** | 它超出授权改了前端组件；我追问「还动过哪些我没要求的地方」后，它列出 4 项超范围改动 |
| **④ 我如何引导** | 追问三个问题：原写法的具体攻击路径、修复是否真正堵住、还有哪些超范围改动。并明确要求「请具体说明攻击路径，不要只说『不安全』」 |
| **⑤ 结果验证** | 六组攻击载荷全部 400；`baseUrl` 指向必然连不上的地址仍返回 200，证明已被忽略 |

### 案例二：限流可被伪造请求头绕过

| 段 | 内容 |
|---|---|
| **① 我的提问** | 指出 `getClientIp` 取 `x-forwarded-for` **第一段**等于完全信任客户端，攻击者换一个伪造值就换一个新配额；要求改成优先 `x-real-ip`、否则取最后一段 |
| **② AI 的建议** | 确认判断，说明 XFF 语义是「代理链追加」、只有最右段由可信入口追加；给出本地与 Vercel 两种环境下的行为差异表 |
| **③ 我发现的问题** | 它主动说明了一个我原本没意识到的前提：**该修复的有效性依赖「部署在可信反向代理之后」**，否则客户端仍可同时伪造两个头 |
| **④ 我如何引导** | 我要求它说明「本地 dev 与 Vercel 分别是什么行为」，这个约束逼出了上面那张双列对比表 |
| **⑤ 结果验证** | 连发 12 次请求，第 11 次起返回 429；换 `x-real-ip` 后重新获得配额；伪造 XFF 第一段不再能换桶 |

### 案例三：README 宣称的功能在代码里不存在（自己发现的文档不一致）

| 段 | 内容 |
|---|---|
| **① 我发现的经过** | 做全量审计时对照 README 与代码，发现 README 第 26 行写着「接口限流时自动重试」，而提交 `18bf2c3` 的说明也写了「含 429 限流自动重试」——但当前 `route.ts` 里搜 429 只有我们自己的限流。对照 10-13 的备份，确认该能力在 10-14 重建项目时丢失，而文档未同步 |
| **② 我的判断** | 这是「按 README 操作却发现功能不存在」的一类问题，会直接影响评审对整份材料的信任。我选择**恢复功能**而不是删掉文档描述 |
| **③ 我如何引导** | 要求它先确认代码现状（不要依据提交说明推断），再做最小实现：只对 429 重试、其他状态码不重试、重试必须发生在任何 SSE 字节写出之前 |
| **④ 它做对的地方** | 重试前调用了 `upstream.body?.cancel()` 丢弃 429 响应体以释放连接 —— 这个细节我没有要求，是正确的 |
| **⑤ 结果验证** | 把模型临时指回被限流的 `glm-4.7-flash` 触发真实 429，返回的是**只在重试之后才存在的专门错误文案**（`模型接口当前访问量过大（HTTP 429）`）；改前该场景走通用分支，显示的是 `模型 API 请求失败（429）`。**文案本身即证明重试路径执行了** |

## 5.4 我从这些纠错里总结的规则

1. **让 AI 先解释成因再改代码。** 否则它会跳过诊断直接动手，改出来的东西可能只是「看起来对」。
2. **"不要破坏 X" 是无效约束，"除 A、B 文件外不得修改" 才有效。** 前者是主观判断，模型有自己的理解。
3. **一次只改一件事。** 否则出错无法归因，而且会让 diff 难以审查。
4. **要求它给出理由，而不只是结果。** 有理由的地方才是我能审查的地方。
5. **安全类改动，验收用例必须我自己构造。** 不能接受「它说修好了」。
6. **在 Prompt 里预先给它一个「可以诚实说不知道」的出口。** 我写「如果无法端到端验证，请如实说明原因，不要编一个测试方法」，它就没有虚构，而是说明了自己只验证到机制层。

在删掉 `node_modules`（635 MB）后从零安装的实测结果（Windows 11 / Node v24.19.0 / npm 11.17.0，走仓库内 `.npmrc` 指向的国内镜像）：

| 步骤 | 实测结果 |
|---|---|
| `npm install`（469 个包） | **15.1 秒**，退出码 0，无报错 |
| 首次打开首页（`npm run dev`，含按需编译） | **3.9 秒** |
| 同一页面第二次访问 | **0.05 秒** |
| `/api/chat` 一次真实调用（含模型生成） | **1.88 秒** |
| `/api/health` | 200，返回 `keyConfigured: true`、`model: "glm-4-flash"` |

三件值得记下来的事：

1. **镜像源的影响是决定性的。** 同一份 `package-lock.json`，走默认源时这个项目历史上出现过 `ECONNRESET` 导致安装中断；改用镜像后 15 秒装完。所以我把 `.npmrc` 一起提交进了仓库 —— 复现速度不该由网络状况决定。
2. **开发模式的首屏慢主要来自「编译」，不是「加载」。** 3.9 秒里大半是 Next.js 首次访问时按需编译该路由，编译一次之后同样的页面只要 0.05 秒。这解释了为什么会觉得「第一次打开特别慢」，也说明**演示时换用生产模式就能绕开这一项**。
3. **编辑器资源是另一笔独立开销。** 页面本身 3.9 秒就绪，但代码编辑器还要单独从 CDN 拉约 3.6 MB。已改为国内镜像并加 `preconnect`，实测该文件下载时间从 1.80 秒降到 0.83 秒。

> 写作提示：如果实测发现某个步骤卡住，**把卡点和解决办法写进来是最加分的**——那证明你真跑过。

# 7. 工程权衡与局限

> 主动写局限是加分项。被问出来才写是减分项。

| 项 | 现状 | 为什么这样取舍 |
|---|---|---|
| **限流** | 计数器存于服务进程内存 | **本地与单实例自托管有效；部署到 serverless 后各实例独立、冷启动重置，等于尽力而为。** 严格全局限制需接 KV/Redis，本期未实现 |
| **限流的信任前提** | 依赖入口覆写 `x-real-ip` / XFF | 部署在 Vercel、EdgeOne 等可信入口后时有效；**裸机直连公网时两个头都可伪造，需在反向代理层剥离或改用 TCP 层地址** |
| **自定义接口地址** | 仅限自带密钥 + https + 域名白名单 | 开放性让位于安全性。完全放开会造成凭据外泄与 SSRF；白名单只校验第一跳，故上游重定向也一并禁止 |
| **用户自带 Key 的存储** | 明文存于浏览器 `localStorage` | 便利优先。**风险已在界面上明示**：同源 XSS 或浏览器扩展可读取，公共电脑不应保存。改用服务端托管需要账号体系，超出本期范围 |
| **对话历史** | 存 `localStorage`，不上传 | 隐私优先。代价：换设备/清缓存即丢失 |
| **数据持久化** | 无服务端存储、无用户系统 | 减少攻击面；代价：无法跨设备同步 |
| **模型** | 默认使用免费模型（`glm-4-flash`） | 成本为零；代价：**高峰期限流严重**（实测 `glm-4.7-flash` 曾持续返回 429），复杂任务质量一般。已提供 `LLM_MODEL` / `LLM_BASE_URL` 环境变量，可在不改代码的前提下更换模型甚至服务商 |
| **错误知识库** | 内置静态数据（309 行） | 覆盖常见类型；代价：罕见错误匹配不到，会回落给模型解释 |
| **验证深度** | 部分防护只验证到代码审查层 | 例如「禁止上游重定向」无法在本机端到端复现——需要一个在白名单内、且会返回 302 指向内网的上游，真实厂商无法被诱导，本地 http 地址又过不了 https + 白名单校验。**此处只验证到机制层，未做端到端攻击验证** |

功能层面我没有主动砍掉过东西——能做完的都留在里面了。

但**选题层面我砍掉过五个方向**（见 1.1 的表格）：自然语言查询数据、报错诊断与能力画像、代码执行可视化、多角色对抗质询、截图转可编辑表格。理由各不相同，最直接的是代码执行可视化——同类成熟项目已经存在（Python Tutor 系列），我做得再好也只是重复；截图转表格则是开发量约 35 小时，剩余周期放不下，最后做成了独立仓库单独保留。

这两次放弃让我确认一件事：**判断「不做什么」，比判断「做什么」更能决定项目能不能按时交。**
