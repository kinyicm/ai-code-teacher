## 1. 我的提问

（原文照录）

```
我审查 /api/chat 时发现一个安全问题，请先确认我的判断，不要直接改代码。

【现象】
route.ts 里这两段连起来有问题：
  const baseUrl = (body?.baseUrl ?? "").trim() || API_URL;
  const apiKey = clientKey || serverKey;
  upstream = await fetch(baseUrl, { headers: { Authorization: `Bearer ${apiKey}` } });
也就是说：如果客户端传了 baseUrl 但不传 apiKey，服务端会用自己的
ZHIPU_API_KEY，并把 Authorization 头发到这个由客户端指定的 baseUrl。

【我的判断】
1. 这是个凭据外泄路径：攻击者把 baseUrl 设成自己的域名，就能拿到服务端 Key
2. 同时这也是 SSRF：baseUrl 完全不受限，可以让服务器去请求内网地址
   或 169.254.169.254 这类云元数据接口

【请求】
1. 先确认这两个判断对不对，说明成因
2. 再给修改方案，要求满足：
   - 只要是「使用服务端内置 Key」的分支，baseUrl 必须强制等于默认 API_URL，
     客户端传的值在该分支下直接忽略
   - 自定义接口地址仅在「客户端自带 Key」模式下允许使用
   - 自定义地址必须加白名单，且只允许 https
   - 不能破坏现有的「自定义模型接口」功能（模型设置面板要照常可用）
3. 说明会改哪些文件，以及我该怎么验证修复生效
4. 不要动 docs/，不要新增依赖
```

## 2. AI 的修改建议

AI 先报了一件事：**主项目目录 `d:\Projects\AI-Code-Teacher` 已不存在**，它搜索磁盘后定位到桌面目录，
并核对 `.git` 当天仍有更新，确认那才是当前版本——才开始分析。

### 2.1 两个判断都成立（AI 原文摘录）

> **判断 1（凭据外泄）成立。** 当请求带 `baseUrl` 但不带 `apiKey` 时：`apiKey = serverKey`、
> `baseUrl = 客户端地址`，`Authorization: Bearer <ZHIPU_API_KEY>` 被原样发往攻击者控制的域名。
> 这是标准的 Secret Exfiltration，且**不需要任何绕过**——就是正常的请求组合。
>
> **判断 2（SSRF）成立。** `baseUrl` 无任何校验，`fetch` 可指向任意地址。攻击者可让服务器请求
> 内网地址、`http://169.254.169.254/...` 云元数据等；而且即使攻击者自带 Key（无 Key 外泄价值），
> SSRF 本身依然存在，因为请求是**由服务器发起的**。

### 2.2 给出的修改方案

**按分支强制（对应我的约束 1、2）**：

```ts
const clientKey = (body?.apiKey ?? "").trim();
const serverKey = process.env.ZHIPU_API_KEY || "";
const apiKey = clientKey || serverKey;
const usingServerKey = !clientKey;

let baseUrl: string;
let model: string;
if (usingServerKey) {
  // 服务端内置 Key 分支：地址与模型一律强制默认，客户端传值直接忽略（防凭据外泄）
  baseUrl = API_URL;
  model = MODEL;
} else {
  // 自定义 Key 分支：地址必须通过白名单 + https 校验
  const err = validateCustomBaseUrl(body?.baseUrl);
  if (err) return jsonError(`自定义接口地址无效：${err}`, 400);
  baseUrl = (body?.baseUrl ?? "").trim();
  model = (body?.model ?? "").trim() || MODEL;
}
```

它还补了一句：模型名在服务端 Key 分支也一并强制默认，属**纵深防御**——该模式下客户端本来
也没有合理理由指定模型。

**白名单 + 仅 https（对应约束 3）**：新增 `ALLOWED_CUSTOM_HOSTS` 常量
（openai / deepseek / moonshot / dashscope）与 `validateCustomBaseUrl()`，
逐项校验：非空 → URL 合法 → `https:` → 无账号密码 → 端口仅 443 → `hostname` 精确匹配白名单。

> AI 的说明：域名级白名单天然挡掉 IP、内网段、`169.254.169.254`、DNS rebinding 等 SSRF 路径；
> 白名单是单个常量，日后加服务商只改这一处。

## 3. 我发现的问题

### 3.1 它超出我的要求改了前端（我追问后才承认）

我明确的要求只有 4 条（见第 1 节约束），但实际改动里还包括 **`ModelSettings.tsx`**：

> **Q3：那次改动中超出明确要求的部分**
> 1. **ModelSettings.tsx**：保存前用 `validateCustomBaseUrl` 预校验 + 自定义卡片文案改为
>    「仅限白名单域名」——**你没要求改前端**。理由：配套 UX，否则用户填白名单外地址
>    只能等服务端 400，且改文案避免误导。
> 2. **错误文案与注释**：route.ts 里「安全约束」注释块、`自定义接口地址无效：…` 错误格式。
> 3. **白名单放公共模块**：`ALLOWED_CUSTOM_HOSTS` 放 modelConfig.ts，前后端共用单一来源。
> 4. 遵守约束：没动 docs/、没新增依赖、没新增文件。

**我的判断**：第 1 条是真实的越界——我要求"不要破坏自定义模型功能"，它转而修改了这个功能的
前端行为。虽然动机合理（配套 UX），但**安全相关的改动被扩大到 UI 层，是我要审查的**。
第 2、3 条属于实现细节，可接受。

### 3.2 它主动指出了我没想到的残留风险

> **残余理论风险**：`fetch` 默认跟随重定向（undici 最多 20 跳）。若某个白名单厂商被诱导
> 返回 302 指向内网地址，请求仍会发出。但按 Fetch 规范，**跨域重定向会剥离 Authorization 头**，
> 且该分支的 key 是客户端自己的——所以没有凭据外泄，只剩一次「无凭据的连通性探测」。
> 若要绝对严谨，可给 `fetch` 加 `redirect: "error"`。

**这条比我原本的判断更细**：我只想到"重定向能绕过白名单"，它补充了"Authorization 会被剥离，
所以不是凭据外泄，只是连通性探测"。这个区分是准确的，我接受。这也是第 3 条 Prompt 链的由来。

### 3.3 它还顺手报了另一个问题

> ⚠️ `next build` 在预渲染内置页面 `/_global-error` 时报错 `TypeError: Cannot read properties
> of null (reading 'useContext')`（Next.js 16.4 + cacheComponents）。与本次改动无关，但会阻塞部署。

**后续核实**：清空 `.next` 后重新构建，该错误**不再复现**（8.5 秒构建成功）。属缓存状态导致的
偶发失败，不影响交付。

### 5.2 自定义模式下的六组攻击载荷 —— 全部被拒（生产模式 `next start` 实测）

| 载荷 `baseUrl` | 预期拦截点 | 实测 |

### 5.3 服务端 Key 分支：`baseUrl` 被完全忽略

**验证思路**：把 `baseUrl` 指向一个**必然连不上**的地址。如果它被使用，一定失败；如果被忽略，
会走默认智谱接口并正常返回。

```
请求: {"baseUrl":"https://127.0.0.1:1/never","messages":[{"role":"user","content":"say ok"}]}
实测: HTTP 200，正常流式输出 data: {"content":"Okay"}
```

**结论**：请求走的是默认接口，客户端传入的 `baseUrl` 已被丢弃，凭据外泄路径封堵。

## 6. 我从这条链学到的

**安全边界必须由我来定，而且要写成可检验的约束。** 我第一版只写"不要破坏自定义模型功能"，
结果它把这个功能的前端行为改了——因为"不破坏"是我的主观判断，它有自己的理解。
如果写成"除 route.ts 与 modelConfig.ts 外不得修改其他文件"，就不会有这个越界。

**另一条**：追问"请具体说明攻击路径，不要只说'不安全'"，是让它给出推理而不是结论的关键。
